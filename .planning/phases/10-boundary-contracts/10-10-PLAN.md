<objective>
Fix the confirmed root cause of the recurring Copilot OTEL real-token-capture gap (10-UAT.md gap 1, `.planning/debug/copilot-otel-real-capture-recurrence.md`): Copilot CLI 1.0.67 only initializes/writes OpenTelemetry (including the `COPILOT_OTEL_FILE_EXPORTER_PATH` file exporter) when invoked with an explicit `-p`/`--prompt` flag (non-interactive argv-prompt mode). Prevue's `copilot-cli` `CliEngineSpec` uses `prompt_delivery="stdin"` with no `-p` in `base_argv`, so the real production invocation shape never triggers OTEL export — regardless of the parser (`usage.py::_parse_copilot_otel`, confirmed correct), the env wiring (`COPILOT_OTEL_FILE_EXPORTER_PATH`, confirmed correct), or the CLI version pin (1.0.67, confirmed correct).

This is a **code-only fix** in the adapter's prompt-delivery mechanism, constrained by a genuine, previously-encountered production failure: Phase 1 (01-07-PLAN.md) originally used `-p` for Copilot and hit a live ARG_MAX crash (`[Errno 7] Argument list too long`) on a real large PR diff, which is why the codebase moved to stdin delivery in the first place. This plan does not re-introduce that regression. Instead of switching unconditionally to `-p`, it adds a size-gated delivery mode: use `-p` argv delivery only when the assembled prompt fits comfortably under a conservative, well-under-ARG_MAX byte ceiling (reaching the OTEL-emitting code path for the common case — small-to-medium PRs); fall back to the existing proven-safe stdin delivery for anything at or above that ceiling (identical behavior to today, `estimated=True`, no crash risk). `usage.py`'s parser, the workflow YAML's `COPILOT_OTEL_FILE_EXPORTER_PATH` wiring, and the CLI version pin are all already correct per the debug session and are NOT touched by this plan.

Purpose: Make real (non-estimated) Copilot token/cost accounting per PERF-03/D-04 actually reachable in production for the PR sizes where it matters most, without reintroducing a previously-fixed crash class.
Output: `CliEngineSpec` gains a size-gated `"stdin-or-argv"` prompt-delivery mode with a concrete byte ceiling; `copilot-cli`'s spec adopts it; `cli_adapter.py`'s `_invoke` implements the branch; existing tests that hard-coded "copilot never uses `-p`" are updated to the new size-gated contract; docs describe the size-gated fallback.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|--------------|
| Assembled review prompt (contains diff content from the PR under review, already fenced as UNTRUSTED DATA) -> subprocess argv (`-p <prompt>`) | Moving prompt content from stdin to an argv element does not change trust posture (the prompt was already untrusted-data-fenced before this plan and stays so) but does change the OS-level delivery channel, which has a real, previously-encountered failure mode (ARG_MAX) this plan must not reintroduce. |
| `spec.argv_prompt_max_bytes` (declarative spec constant, not consumer-configurable) | The size ceiling is a hard-coded, non-configurable safety constant in `spec.py` — a malicious or oversized PR diff cannot influence which delivery mode is chosen beyond naturally producing a larger prompt, which only ever pushes the decision toward the *safer* (stdin) branch, never toward argv. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-10-10-01 | Denial of Service | `cli_adapter.py` `_invoke` "stdin-or-argv" branch — a prompt sized just under the ceiling on a runner with an unusually large pre-existing environment block | mitigate | Ceiling (64 KiB) is set with a wide safety margin (an order of magnitude below the ~1-2 MB range ARG_MAX limits typically occupy) specifically because 01-07's real crash occurred near the ~1 MB `MAX_PROMPT_BYTES` ceiling, not near 64 KiB; regression test `test_oversized_prompt_falls_back_to_stdin_not_argv` locks in that oversized prompts never reach the argv branch. |
| T-10-10-02 | Tampering | Prompt content is attacker-influenced (PR diff) but delivery-channel selection depends only on its byte length | accept | The byte-length check is a pure size comparison with no interpretation of prompt content; an attacker can only push their own prompt into the safer (stdin) branch by making it larger, never force smaller/benign-looking prompts into an unsafe state — no exploitable behavior difference in what content reaches the CLI either way (same fenced UNTRUSTED DATA framing on both branches, per existing `prompt.py` construction, unchanged by this plan). |

</threat_model>
